# Registry sweep, 2026-08-22 (#6198)

Every key row of `tex/tenkz/tenkz-language-registry.tex` settled against the
implementation by compiling: what the key accepts, what it changes on the
page, the stated default, the description, and the cited consumers.  Eight
compile agents swept the sixty-seven key rows; fifty stood accurate and
seventeen took a correction, executed in the change that adds this record.
Source line numbers below refer to the sweep-time tree; named functions are
the stable anchors in the current source.
Two agent verdicts were themselves corrected on re-review before anything
moved: `kernel-wire:crossing` is read by the hull-route habit pass
(`route_habit`), which the sweep's scenarios never exercised, and the
`kernel-picture:align` baseline effect is real; both rows keep their keys.

## The seventeen corrected rows, with their full compile evidence

### `kernel-atom:name` — reword

**Resolution:** row default corrected to none; contract table synchronized.

name=anchor compiles and is functionally addressable: `at=1 e of anchor` resolves correctly (tnlog shows atom\|...\|name=anchor). ports/at etc. all read the {name} field (tenkz-kernel.code.tex:1415-1424, 2031, commit registers named_prop only when the field is staged). HOWEVER the claimed default 'generated' does not hold: when name= is omitted, tnlog emits no name= field at all, and guessing the internal model id (atom-1) or node id (addr-1) as an address both fail with TKZ-KERNEL-RENDER-CROSSREF ('names no string or leg of this picture') -- confirmed by direct probes (name_gen_ref.tex, name_gen_ref2.tex, name_gen_ref3.tex, all exit 1). Code at commit (line ~1414-1424) only registers a name when the stage prop actually holds one; no fallback generator exists in tenkz-kernel.code.tex for the atom name= key. This 'generated' default phrasing is shared boilerplate across many registry rows (per docs/tenkz/LANGUAGE-1.0.md lines 135/192/234) and is not literally true for a plain unnamed \tn atom -- unnamed atoms remain addressable only via their (row,col) coordinate (a property of `at=`, not of `name=`), not via any auto-minted name string.

### `kernel-declare:hue` — reword

**Resolution:** row states what the source: prefix does today.

Compiled p_hue_plain (hue=red), p_hue_source (hue=source:red), p_hue_none (species declared with no hue at all, gets house-cycle hue), and p_hue_bad (hue=notacolorxyz). ACCEPTS: legal color names accepted; illegal name refused at render time ('Package xcolor Error: Undefined color'). DEFAULT 'house cycle' matches: an undeclared-hue species takes the next \c__tenkz_speccycle_clist slot (tenkz-core.code.tex ~1579-1595). DESCRIPTION issue: p_hue_plain.png and p_hue_source.png are byte-identical (cfae3fe...) -- the regex at tenkz-kernel.code.tex:2608-2614 makes the 'source:' prefix a pure no-op that is stripped before use; 'red' and 'source:red' resolve to the exact same literal color token with no palette lookup table anywhere in tex/tenkz (grep for a source-name mapping table found nothing). So 'source:* reproduces a cited palette' overstates what happens: source: is inert syntactic sugar with no distinct effect from writing the color name bare -- there is no palette-fidelity mechanism, only a stripped prefix.

### `kernel-mark:label pos` — reword

**Resolution:** row states compass word or degree value.

Registry: angle, default auto. lp_default/lp_n/lp_s/lp_45 probes (form=label mark) on a 2-atom row: omitting the key gives raster hash c1d880… identical to explicit 'label pos=n' (same hash), while 'label pos=s' (0c1813…) and 'label pos=45' (963f48…) each differ — confirms the key repositions the label and that the computed 'auto' default happens to resolve to north here (.tnlog for the omitted case has no 'label-pos=' token at all, so the default really is 'field absent, computed at render time', not a literal spelling). ACCEPTS is broader than 8 named words: label pos=45 (a bare numeric degree) compiles and renders at a distinct position, because tex/tenkz/tenkz-kernel.code.tex's \__tenkz_kernel_r_compass:n (line 5331) only special-cases the 8 compass words {n,ne,e,se,s,sw,w,nw} via str_case and passes any other token straight to cosd/sind as a raw angle. An actually-illegal word (label pos=bogus) is NOT rejected by the kernel-mark key parser itself (the key is registered as a raw '.value' with no validation) — it compiles past record-building and only fails later, at a generic (non-tenkz-branded) LaTeX error: '! LaTeX Error: Unknown fp word bogus.' Likewise 'label pos=auto' (the literal word used to describe the default) is itself illegal and fails the same way — 'auto' is descriptive of the absent-key behavior, not a spellable value. Description 'Label quadrant.' undersells this: the mechanism is a full compass bearing (8 named points) plus arbitrary numeric degrees, not a 4-way quadrant choice.

### `kernel-mark:name` — defect

**Resolution:** row states no address grammar resolves a mark yet.

Registry: identifier, default generated, description 'Addressable name.' ACCEPTS/DEFAULT check out: name=R parses fine and .tnlog shows the omitted-key case gets an auto id (id=mark-3); name=self is refused with a dedicated message '[TKZ-LANG-NAME-RESERVED] name self is reserved by the address grammar', matching the reserved-word guard in \__tenkz_kernel_commit: (tenkz-kernel.code.tex ~1415). But the 'Addressable' half of the description does not hold up under test: name= on a \tnmark IS written into the shared \l__tenkz_kernel_named_prop table (generic bookkeeping shared with atoms/wires — a real read site, at commit and at every \__tenkz_kernel_dep_add call), yet every natural way to actually use that registered name to reference the mark fails. Probed all three plausible consumers: (1) nm_named.tex — a second \tnmark[form=label]{R}{...} targeting the named enclosure mark 'R' as a node — fails: '[TKZ-GEOM-UNPLACED] no placement named mark-3' (marks are never given a geometry placement); (2) nm_unnamed_ref_fail.tex / a wire-crossing-style reference to 'R' — fails: '[TKZ-KERNEL-RENDER-CROSSREF] crossing operand R names no string or leg of this picture'; (3) nm_selector_ref.tex — a second \tnmark[form=enclosure]{R}{...} using 'R' as a cell-selector term — fails: '[TKZ-KERNEL-SELECTOR-KIND] the selection R does not resolve only to atoms or a range of cells'. All three errors show the name-to-id substitution succeeding (each message names the resolved mark-3/R correctly) and failing only at the next stage, confirming there is currently no functioning way to address a mark by its registered name — the description's core claim is false in practice even though the field is mechanically stored.

### `kernel-picture:align` — defect

**Resolution:** fixed: a dedicated validator refuses anything but midline or a row number.

align only shows a page effect when the tenkz picture sits inline against surrounding text/glyphs, since it sets the tikzpicture's `baseline=` option (tenkz-kernel.code.tex:20034), not the picture's own ink layout. Probe 'X\begin{tenkz}[rows={ket,op,bra},cols=1,align=<v>]...\end{tenkz}Y': align omitted vs align=midline give identical rasters (7d6685c...), confirming default=midline; align=1 and align=3 each give distinct rasters (b0dd289... and b1247b8...) from the default and from each other, confirming a real baseline-shift effect (description 'The wire axis panels align on.' is accurate for legal input). BUT align is type-labeled 'row' with no dedicated validator (wired through the raw \__tenkz_kernel_value:nnn, tenkz-kernel.code.tex:1240, same gap as cols=): align=bogus does not refuse cleanly -- it crashes deep in fp_eval with a bare 'LaTeX Error: Unknown fp word bogus.' and a cascading '\??? doesn't match its definition' error, not a [TKZ-*] diagnostic. This is a genuine ACCEPTS-criterion failure paralleling cols=. Probes: align_midline/align_row1/align_row3/align_omit/align_bogus.tex.

**Resolution:** fixed: the key rides a picture-scope positive-integer validator with its own diagnostic.

cols omitted vs cols=3 explicit (with rows={ket}, 3 populated cells): identical raster (d66b63e...), confirming default=3. cols=2 vs cols=3: distinct raster (fewer populated cells), confirming real page effect. ### `kernel-picture:planes` — defect

**Resolution:** fixed: same flag semantics as sandwich.

Sugar expansion itself is faithful: on a lattice=1x1 two-member-basis picture, planes and frame={plane, basis={ket at (0,0), bra at (2,2)}} (direct) render byte-identical PNGs (sha256 1f8ec40a...). (Also note: combining planes with the picture-level physical= policy is separately refused with '[TKZ-FRAME-BASIS-POLICY] displaced or multi-member bases require explicit wires; picture policy physical has no member-level meaning' -- an orthogonal, correctly-diagnosed constraint, not itself a defect.) ### `kernel-picture:sandwich` — defect

**Resolution:** fixed: flag-shaped sugar validates true|false; false expands nothing and still counts as the sugar spelling under strict.

sandwich sugar expansion itself is faithful: \begin{tenkz}[sandwich,...] and \begin{tenkz}[rows={ket,op,bra},...] with identical bodies produce byte-identical PNGs (sha256 8e37fb7b...). BUT the row's stated type is 'flag' (implying true/false semantics like the genuine flag helper __tenkz_kernel_flag:nnn used for conjugate/closed/tint, which validates true\|false and errors on anything else, tenkz-kernel.code.tex:1006-1025). sandwich is NOT built with that helper -- its .code:n unconditionally runs \__tenkz_kernel_sugar:n{sandwich} + keys_set rows={ket,op,bra} regardless of the value #1, which is never inspected (tenkz-kernel.code.tex:1257-1261). Tested sandwich=maybe (compiles, rc=0, no error) and sandwich=false (with rows left unset otherwise): sandwich_false_only.png is byte-identical to bare sandwich (sha256 8e37fb7b... both), i.e. sandwich=false silently behaves exactly like sandwich=true, not like the stated default 'false'/absence. A user writing sandwich=false to opt out gets the opposite of what the flag type promises, with no error. Recommend the type field read something like a valueless toggle rather than 'flag', or the implementation be fixed to honor true/false via the same helper other flags use.
